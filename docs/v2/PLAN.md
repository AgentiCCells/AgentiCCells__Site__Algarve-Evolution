# Plan, then apply: the hub's review queue (contract)

Dinis Cruz, 16 November 2026: "Yes, can you build it?" (the plan-then-apply pattern from "Odoo's agents can now write to the system of record", https://newsroom.sgit.ai/articles/odoo-and-our-stack.html: snapshot, plan, policy check, signed approval, broker, record).

## In the browser: window.HUB.plan (src/hub/hub.js)
- `HUB.plan.add(item)` -> id. item = { source: "<page or workflow id>", title: "<what this does, in a sentence>", calls: [ { method: "POST", path: "/json/2/<model>/<method>", body: {...} } ], policy?: { agent: "<cell or page>", grant: [...], mandate: "...", checks: [ { rule, ok: bool, note } ], needs_approval: bool }, refs?: [ "<feed ids>" ] }. Stored in localStorage ("hub-plan"), shown with a count in the header, kept in this browser only.
- `HUB.plan.list()`, `HUB.plan.remove(id)`, `HUB.plan.clear()`, `HUB.plan.on(fn)` (called with the list after each change).
- Every `<details class="odoo-call">` on any page gets an "Add to plan" button automatically (hub.js reads the verb, path and JSON body from the panel), so pages need no changes; pages and workflows may also call HUB.plan.add directly with a policy.

## The Plan page (/plan/)
The AE team reviews every proposed change: grouped by source, each with its calls, its policy checks and its references. Approve or reject per item. Approving signs: the browser makes an ECDSA P-256 key pair for the reviewer (kept in this browser; the public half shown as a fingerprint), and signs the canonical JSON of the approved plan. Export: a signed plan file (plan.json: { v:1, created, reviewer: { name, publicKeyJwk, fingerprint }, items: [...], signature }), and a copy of the private key never leaves the browser.

## The broker (scripts/odoo/apply-plan.mjs)
`node scripts/odoo/apply-plan.mjs plan.json [--apply]`: verifies the signature and that the reviewer's key is in an allow list (scripts/odoo/reviewers.json; empty by default, a key is added by a person), checks every call against the broker's own policy (allowed models and methods only; no unlink; no writes to res.users or access rights), then dry-runs (default: prints what it would do) or applies to the experimentation Odoo through the JSON-2 API with a dedicated user that may write only hub models, and appends a record of what was applied (plan hash, reviewer fingerprint, results) to scripts/odoo/applied/<date>.jsonl. Never against Algarve Evolution's official Odoo.

## As built (16 November 2026, odoo@AgentiCCells.dinis)
Where the build differs from or adds to the contract above:
- **Items.** `HUB.plan.add` also stores `id`, `added` (ISO), `page` (the path it came from) and `snapshot` ({ feed: "public", exported } of the feed the page read), and keeps `simulated: true` when given. Adding the same calls from the same source again returns the existing id. Extra methods: `HUB.plan.get(id)` and `HUB.plan.find(calls, source?)`. The header count is a link to /plan/ next to the feed state (added by hub.js; hidden while the plan is empty, except on /plan/).
- **Panels.** The automatic button reads the verb (`.odoo-call-verb`), the path (`summary code`, or the first `/json/2/...` in the `<pre>`), and the JSON body (from the first line of the `<pre>` that starts with `{` or `[`). Panels that sit together in one container are one action of several calls (find, then create, then rank): the button adds them as one item ("Add these 3 calls to plan"). A panel with `data-plan="off"` gets no button (use it where a page adds items itself with HUB.plan.add, as the Workflows page does). Pressing the button again removes the item; its state follows the panel's current text, so editing a form after adding shows "Add to plan" again.
- **Policy.** The broker's policy is one file, `src/hub/plan-policy.js` (globalThis.PlanPolicy): the Plan page runs it in the browser to show each item's checks before anyone signs, and the broker loads the same file and runs it again. It allows create and write on the hub models (aih.programme, aih.programme.company, aih.session, aih.kpi, aih.reflection, aih.challenge, aih.application, aih.vibathon, aih.vibathon.jury, aih.vibathon.participant, aih.project, aih.project.score, aih.community), `action_compute_matches` on aih.challenge, `message_post` on aih.project, reads on aih.skill, aih.hub, aih.activity, res.partner.category and event.event, and on res.partner create, write and activity_schedule with the `aih_` fields plus name, email, phone, is_company, city, website and category_id. Never: unlink, private methods, res.users, res.groups, res.company, res.config, ir.*, base.*, mail.*, bus.*. At most 20 calls an item, 50 records or 200 ids a call. Values still in angle brackets fail the check, except references to an earlier call of the same item ("<id from step 1>", "ids from call 1", "<id returned by the first call>"), which the broker resolves to that call's result, and "<model: name>", which it looks up by exact name.
- **Review.** Approve, reject or remove per item; an item whose checks fail cannot be approved. Only the "Algarve Evolution team" persona reviews for real (mode "review"); others see the queue read only and may switch on a demo (mode "demo"), which the broker refuses. Two example items (simulated, built from the feed at build time) are added on a first visit; "Add the two examples" brings them back.
- **Signing.** The key pair is made with WebCrypto (ECDSA P-256), the private key non-extractable and kept in IndexedDB ("hub-plan"). Fingerprint: SHA-256 (hex) of the canonical JSON of { crv, kty, x, y }. Canonical JSON: keys sorted at every level, no spaces. The signature (base64url, raw r||s) is over the canonical JSON of the whole plan without `signature`. plan.json: { v: 1, created, mode: "review"|"demo", hub, reviewer: { name, publicKeyJwk, fingerprint }, items: [ approved items, each with review: { decision, at } ], rejected: [ ids ], signature }. The Plan page verifies an imported plan.json in the browser (signature, fingerprint, mode, whether the key was on reviewers.json at build time, the policy).
- **Broker.** `node scripts/odoo/apply-plan.mjs plan.json [--apply] [--reviewers <file>] [--record-dir <dir>] [--again]`; settings ODOO_URL, ODOO_DB, PLAN_BROKER_API_KEY(_FILE), PLAN_ODOO_HOSTS. Target: loopback or a host named in PLAN_ODOO_HOSTS, never algarveevolution.pt, and the database must hold an aih.hub record. Snapshot: before writing to existing records it reads their current values (kept in the record as `before`); an item whose records changed in Odoo after the item's snapshot is skipped. Each JSON-2 call is its own transaction, so a failure half way through an item is reported as "partly applied". Only `--apply` appends to scripts/odoo/applied/<date>.jsonl (see its README); a plan already recorded is not applied again without `--again`.
- **Odoo user.** Addon 19.0.1.3.0 adds the group "Innovation Hub / Plan broker" (create and write on the hub models above and on res.partner, no unlink; implies Feed reader). scripts/odoo/accounts.py creates the user `plan-broker` (Internal User + Plan broker) and its API key in /root/.agents/odoo/plan-broker-api-key. As an internal user it can still read what internal users read and edit its own preferences; the broker's policy is what keeps its writes to hub records.
- **Tested** on 16 November 2026: items added in Chromium from Challenge Connect ("Post a challenge", three calls) and INC/ACC (a founder's KPI month, by keyboard), plus the KPI example; signed as the team; exported; verified in the browser (and a tampered copy failed); the broker refused the plan while the key was not listed, refused a tampered plan, refused a plan of policy-breaking items, dry-ran it against the local Odoo, then applied it with `--apply` to a throwaway copy of the database (a challenge, ranked; a new KPI month; a KPI correction), refused to apply it twice, skipped the correction on a second dry run because the record had changed since the snapshot, and refused algarveevolution.pt. The throwaway database was then dropped: the experimentation Odoo and the committed feeds are unchanged, and the test reviewer key was never added to scripts/odoo/reviewers.json.
